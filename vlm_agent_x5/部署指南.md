# RDK X5 仪表与现场场景 Agent：板端逐条部署

本目录包含唯一入口 `启动.py`。可以单图运行，也可以持续监听一个图片文件夹；每张图独立执行以下流程：

- **YOLO检出表盘**：调用队友的 `tools/run_onnx.py` 读表，再用X5版InternVL2.5-1B观察目标表盘。输出仪表类型及依据、YOLO原始读数和单位、读数可核对性、表盘可见状态。即使YOLO检测到表盘但没读出数值，也走此分支，读数为null、状态为“待复核”。
- **YOLO没有检出表盘**：把整张图片送给VLM，输出固定五项：现场观察、安全隐患、场景合理性、建议、判断边界。只依据图片可见迹象提出条件性关注点，不认证“安全”或“违规”。YOLO运行失败时不能当作“无表”，会记录失败。

队友[现有X5部署手册](../deployment/rdk_x5/README.md)说明其BPU `.bin` 尚未完成编译及板端数值后处理验收。因此本入口**实际调用的是ONNX Runtime CPU上的队友读表程序**，不是YOLO BPU推理。VLM部分遵照[D-Robotics官方InternVL2.5-1B X5文档](https://developer.d-robotics.cc/rdk_doc/en/rdk_s/Robot_development/boxs/generate/hobot_llamacpp/)使用 `hobot_llamacpp` ROS终端图片模式。场景知识仅记录[国家能源局风险识别正文](https://zfxxgk.nea.gov.cn/2024-10/30/c_1310787370.htm)和[应急管理部现场检查资料](https://www.mem.gov.cn/kp/sgzn/201902/t20190226_366257.shtml)的通用检查方向；不代替本厂规程或设备工况。

## 一、板卡和系统

1. 准备RDK X5及Ubuntu 22.04系统，完成TogetheROS.Bot安装。官方说明要求X5将ION设为1.6GB、CPU设为最高频率。板上打开终端逐条执行：

   ```bash
   sudo apt update
   sudo apt install tros-humble-hobot-llamacpp python3-venv wget
   srpi-config
   ```

   在 `srpi-config` 中设置ION=1.6GB与CPU频率后按其提示重启。这一步是人工配置，程序只能提示，不能代替检查。

2. 重启后核对ROS：

   ```bash
   source /opt/tros/humble/setup.bash
   ros2 pkg executables hobot_llamacpp
   ```

   如果找不到包，先修正系统镜像/TogetheROS.Bot包来源，不要把电脑CPU环境当作板端VLM已可用。

## 二、获取代码与依赖

3. 本地分支推送后，在板端逐条执行：

   ```bash
   git clone https://github.com/19820960710/meter-identification.git
   cd meter-identification
   git switch VLM
   git rev-parse --short HEAD
   ```

   如还未推送，可将当前本地仓库整体离线复制到板卡，再进入仓库根目录；不要在远程 `main` 上找尚未上传的文件。根目录应同时有 `tools/run_onnx.py`、`configs/gauges/` 和 `vlm_agent_x5/`。

4. 安装CPU ONNX读表依赖。该步骤在X5 ARM系统上仍需实测wheel可用性：

   ```bash
   python3 -m venv .venv-x5-agent
   source .venv-x5-agent/bin/activate
   python -m pip install -r vlm_agent_x5/requirements.txt
   python tools/verify_bundle.py
   ```

   若 `onnxruntime` 或OpenCV无适用ARM包，按板卡Python版本和架构选择兼容包后重试；不要改成未验收的BPU读数路径。

## 三、下载VLM模型

5. 执行下载脚本，文件仅存 `vlm_agent_x5/models/`，被 `.gitignore` 排除：

   ```bash
   bash vlm_agent_x5/下载模型.sh
   ls -lh vlm_agent_x5/models/vit_model_int16_v2.bin
   ls -lh vlm_agent_x5/models/Qwen2.5-0.5B-Instruct-Q4_0.gguf
   ```

   `.bin` 是X5视觉编码器，`.gguf` 是配套文本模型；二者必须成对，不能使用PC端Transformers权重或S100的`.hbm`。文件链接和型号来自上述官方文档。下载结束后确认文件非空；当前没有随仓库提供权重。

## 四、配置说明

6. 打开 `vlm_agent_x5/config.json`。相对路径均以 `vlm_agent_x5/` 为基准：

   |字段|含义|默认值|
   |---|---|---|
   |`output_dir`|每次运行的JSON和日志保存目录|`outputs`|
   |`yolo.model_path`|队友CPU ONNX模型|`../models/annotation/meter_labeler_v3/best.onnx`|
   |`yolo.backend`|实际调用方式说明|`onnxruntime_cpu`|
   |`internvl.vit_bin`|X5视觉模型|`models/vit_model_int16_v2.bin`|
   |`internvl.llm_gguf`|配套文本模型|`models/Qwen2.5-0.5B-Instruct-Q4_0.gguf`|
   |`timeouts.yolo_seconds`|单张YOLO最长等待秒数|120|
   |`timeouts.vlm_seconds`|单次ROS模型最长等待秒数|180|
   |`prompts.meter`|检出表盘时的四项提示词|`prompt_zh.txt`|
   |`prompts.scene`|无表盘时的五项提示词|`scene_prompt_zh.txt`|
   |`scene_knowledge`|场景一般检查方向及已核实来源|`scene_knowledge.json`|

   现场需要改模型存放位置时，只修改上述路径；模型文件名必须保持与官方X5配对文件一致。程序不从 `config.json` 推导设备正常工作范围，不做安全阈值判断。

7. **调用前自检**（不会运行模型）：

   ```bash
   python vlm_agent_x5/启动.py --check-env
   cat vlm_agent_x5/outputs/环境检查.json
   ```

   `ready=true` 表示程序检查的文件、Python依赖、Linux ARM64和ROS包均可见；这仍不代表模型能成功推理。`ready=false` 返回退出码2，逐项看 `checks` 中的false。`manual_checks` 指明需要人工核对的系统/ION/频率和版本。自检只读系统与配置，不自动下载或改动系统。

## 五、运行与结果

8. 用已有同图SHA标定的样图做首次读表试验：

   ```bash
   python vlm_agent_x5/启动.py --image samples/images/0.jpg
   ```

   或将 `vlm_agent_x5/input.example.json` 中的 `image` 替换为板端真实**绝对路径**，再运行：

   ```bash
   python vlm_agent_x5/启动.py --request vlm_agent_x5/input.example.json
   ```

   输入字段见 `input.schema.json`。新拍图片SHA不等于旧样图，不能直接沿用旧图像素标定；此时YOLO可能只检测目标，数值状态会是“待复核”。多表图若无法唯一绑定读数，也会“待复核”，不把另一块表的刻度当依据。

9. 用一张现场无表盘的图片跑场景分支，命令相同，只改图片路径：

   ```bash
   python vlm_agent_x5/启动.py --image /absolute/path/to/no_meter_scene.jpg
   ```

   YOLO确实未检出表盘时，`result.json` 的 `mode` 为 `scene`，`scene_items` 包含五个固定字段；整张原图送入VLM。若画面证据不足，“安全隐患”应写未见可确认的可见隐患或条件性关注点，不得输出绝对安全结论。示例见 `scene_output.example.json`。

10. **持续检测图片**。先建一个专用输入文件夹，在另一个终端持续向里面复制或保存图片：

   ```bash
   mkdir -p incoming_images
   python vlm_agent_x5/启动.py --watch-folder incoming_images
   ```

   监听 `jpg`、`jpeg`、`png`、`bmp`、`webp`，仅扫描该文件夹的第一层。启动时已有图片也会处理；一张图文件大小和修改时间连续1.5秒不变后才处理。同一路径同一内容在**本次监听会话内**只处理一次；覆盖为不同内容后会再次处理。重启监听会建立新会话，并重新处理文件夹中现有图片。图片复制时若内容改变，本次结果标为失败；文件写入稳定后继续检测。可用 `--poll-seconds 2 --stable-seconds 3` 调整轮询和稳定等待；通过网络共享目录输入时建议适当增大等待时间。

   在监听终端输入 **`0` 后回车**可在当前图片处理完后退出；按 **Ctrl+C** 可中断正在处理的图片，已生成的结果和中断状态会保存。每次监听在 `outputs/watch_<时间_编号>/watch_session.json` 保存会话记录、每张图的SHA256、状态及对应结果路径，`watch.log` 保存处理事件；每张图仍有独立结果目录。终端会打印会话和图片结果的位置。`0` 是本程序交互命令，不是图片文件名。

11. 单图或持续监听均在终端打印图片结果路径：`vlm_agent_x5/outputs/<时间_编号>/result.json`。同目录包含原图快照 `input.<扩展名>`、`input.json`、`env_check.json`、`yolo/result.json`、`yolo_stdout.log`、`yolo_stderr.log`、`vlm_request.json`、`vlm_stdout.log`、`vlm_stderr.log`、`agent.log`；场景分支另有 `scene_sources.json`，仪表分支可能有 `target_dial.png`。YOLO和VLM均针对已保存的原图快照执行，避免输入文件处理途中被覆盖。`status=completed` 表示两个子程序成功产出可解析结构；`partial`表示保留了YOLO结果但VLM失败或仪表读数不足；`failed`表示上游关键步骤失败；`interrupted`表示手动中断。JSON格式见两个 `*.example.json` 与 `output.schema.json`。

## 六、板端验收时必须记录

- 实际X5系统版本、`ros2 pkg executables hobot_llamacpp` 输出、两模型文件的SHA256和大小、环境自检结果。
- 同一张已标定图片的CPU ONNX读数与现有电脑结果对照；真实新图没有标定时不伪造读数。
- 一张仪表图和一张无仪表场景图的 `result.json`、YOLO检测框、ROS原始输出及耗时。可见异常需要人工复核，不把VLM文本当安全认证。
- 官方终端示例能运行不代表本适配器能解析该版本的终端输出。若ROS在超时前没有输出所需JSON，`status` 会是 `partial`，原话和超时记录保存在日志中；依据实际板端输出修正解析方式后再验收。

**电脑上已完成的检查：** Python编译、单图校验与监听测试通过；持续监听处理了0号真实样图，CPU ONNX读数约0.3776MPa，缺少X5模型使该次结果标为`partial`，YOLO读数与会话记录均已保存；本机生成的无表图进入场景分支。电脑没有X5模型和ROS包，端到端VLM尚未在板卡验证，不宣称板端运行成功。
